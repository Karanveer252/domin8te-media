1. IMPLEMENTATION, high. Any stored plan month that no longer fits the rules aborts the whole daily roll and the hourly reminders, for every client.
- Where: supabase/migrations/20261013010100 (public.roll_plan_cycles, loop at the "for t in select id from public.tenants" line), 20261013011400 (app.guard_plan_cycle, which calls app.picks_valid first), 20261014020000 (the comment says old rows are "LEFT as they are").
- Evidence (BY READING, plus SELECT on TEST):
  - Every UPDATE of a month row (the roll's "set state = ended" and "set state = active") fires the guard, and the guard re-checks picks_valid. A row that no longer fits raises 23514.
  - The roll only catches errors around the carry-over insert. So one bad row aborts the whole function for all later clients. Cron plan_cycle_roll fails daily.
  - public.plan_billing_reminders calls the roll first, so the hourly reminder job fails too and no reminder goes out.
  - On TEST, `app.picks_valid('growth', {social, website})` returns false and `picks_valid('domin8te', all five)` returns false. Both were valid under the old rules.
  - On prod, migration 011100 (backfill) runs before 020000 (Ads+N). Months it wrote for gold or silver clients become invalid. An owner editing plans.picks_allowed later does the same to every month.
  - The 020000 comment claims nothing breaks. That is wrong for the roll.
- Fix:
  - Wrap each client's body in the roll in begin/exception, and open a plan_mismatch item for the failing client.
  - Make the guard skip the picks check when only state, locked_at or confirmed_* change.
  - In 020000, flag or migrate existing non-fitting months.
  - Add a test that rolls a legacy row.

4. IMPLEMENTATION, high. Billing dates drift at month end. The console promises something else.
- Where: set_next_cycle_picks, roll_plan_cycles, override_plan_cycle and the backfill all use `period_end + interval '1 month'` (or `bill - interval '1 month'`). The console's new-client form says "then the 31st of each month, or the last day of a shorter month" (mod-newclient.js:178).
- Evidence (VERIFIED on TEST): 2026-01-31 + 1 month = 2026-02-28, and + another month = 2026-03-28. The anchor day is lost for good. The client-side addMonths in lib/time.js clamps from the anchor, so the browser preview and the database disagree after the first short month.
- Impact: months, reminder dates and "change by" dates shift off the real bill date for anchors on the 29th to 31st.
- Fix: store an anchor day (or bill_day) and compute each period_end as the anchor day in the target month, clamped. Do this in SQL, not in the preview.

5. IMPLEMENTATION, medium-high. "Live at a time" limits are counted as monthly counters.
